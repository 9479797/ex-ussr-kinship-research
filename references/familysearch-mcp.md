# FamilySearch MCP: структурированное чтение и разрешённые изменения

Читайте, если в среде подключён FamilySearch MCP или пользователь просит его настроить. MCP — дополнительный инструмент исследования; отсутствие подключения не мешает браузерному поиску и работе с уже полученными материалами.

## 1. Подключение и установка

Сначала обнаружить доступные инструменты и вызвать `auth_status`: проверить аккаунт, `environment` и `writes_allowed`. При неоднозначном аккаунте или целевом древе до уточнения только читать. Разрешения и ограничения уже поставленной задачи действуют без повторного запроса на каждую обычную операцию.

Если пользователь просит установить MCP, один из вариантов — [bguthro/familysearch-mcp](https://github.com/bguthro/familysearch-mcp). Его документированная upstream-версия рассчитана на **macOS, Brave и Python ≥3.11**, содержит 19 MCP-инструментов и обёртки над 203 API-операциями. Перед установкой сверить актуальные [README](https://github.com/bguthro/familysearch-mcp#readme) и [требования Python](https://github.com/bguthro/familysearch-mcp/blob/main/pyproject.toml): другие форки могут отличаться. Это сторонний сервер, не официальный продукт FamilySearch.

Установить в выбранную пользователем папку отдельное окружение, например:

```bash
git clone https://github.com/bguthro/familysearch-mcp.git familysearch-mcp
cd familysearch-mcp
python3.11 -m venv .venv
.venv/bin/python -m pip install -e .
```

В Codex общая настройка находится в `~/.codex/config.toml`, проектная — в `.codex/config.toml` доверенного проекта. Добавлять нужный раздел в существующий файл, не заменяя остальные настройки. Пример production с заблокированной записью:

```toml
[mcp_servers.familysearch]
command = "/absolute/path/to/familysearch-mcp/.venv/bin/familysearch-mcp"

[mcp_servers.familysearch.env]
FS_ENVIRONMENT = "production"
FS_ALLOW_PROD_WRITES = "0"
```

Путь заменить фактическим. После изменения конфигурации обновить подключение MCP поддерживаемым клиентом способом и повторить `auth_status`. Общая настройка делает те же инструменты доступными другим чатам, но не добавляет возможностей API или прав аккаунта. Описание конфигурации: [официальная документация Codex](https://learn.chatgpt.com/docs/config-file/config-sample).

В базовом сервере `writes_allowed` относится к общим write-инструментам. У расширенного подключения могут быть отдельно разрешённые операции в конкретном приватном древе: сверять их диагностику и фактический scope, а не включать общий production-флаг взамен узкого разрешения.

Если поручение включает изменения, разрешённые guarded write-инструменты upstream включаются значением `FS_ALLOW_PROD_WRITES = "1"` в том же разделе окружения. Наличие флага не определяет целевое древо и не разрешает посторонние изменения. Не включать запись ради обхода отказа инструмента. Для чтения флаг не нужен. Загрузку файлов не включать автоматически вместе с записью: `FS_UPLOAD_ROOT` требует отдельной узкой папки и согласованного объёма передачи материалов.

## 2. Авторизация и среда

- Пользователь входит в нужную среду FamilySearch в поддерживаемом браузере; штатный коннектор сам обслуживает авторизацию. У указанного upstream это сессия Brave и возможный запрос macOS Keychain. Не просить прислать пароль, cookies или токен и не извлекать их самостоятельно.
- `production` и `beta` имеют разные сессии и данные. Проверить `auth_status` после подключения; успешный вход на обычный сайт не доказывает вход в Beta. Beta предназначена для проверки, а не хранения итогового семейного древа.
- При истёкшей сессии можно восстановить подключение и повторить **чтение**. После ошибки записи сначала проверить результат по разделу 5. Не считать HTTP 403 доказательством истёкшей сессии; сохранить фактическое сообщение и ограничить только этот маршрут.
- MCP не отменяет CAPTCHA, права на изображения, условия источника и лимиты. При необходимости входа или проверки пользователя действовать по `browser-and-captcha.md`, не менять аккаунт или среду, чтобы преодолеть отказ.

## 3. Что доступно, а что требует другого маршрута

| Задача | Маршрут и пределы базового upstream |
|---|---|
| Найти человека в Family Tree | `search_tree`: имя, фамилия, дата/место рождения. Совпадение — кандидат, а не установленная личность. |
| Прочитать карточку и семью | `get_person`, `get_relatives`; сохранить ID, исходные сведения и ссылки. |
| Проверить источники и подсказки | `get_person_sources`, `get_person_memories`, `get_matches`; описание источника или Memory не заменяет чтение оригинала. |
| Найти индексированную запись | `search_records`: имя/фамилия, `count`, `offset`. В этой обёртке нет фильтров DGS, коллекции, даты, места, родителей или супруга. |
| Уточнить другие API-возможности | `list_operations`, `describe_operation`, затем подходящий `call_operation`. 203 операции — каталог обёрток, не гарантия, что каждая проверена или доступна этому аккаунту. |
| Приватное отдельное древо | Сверить реальные инструменты, целевой tree ID и права. Наличие API-описания не означает, что базовые write-инструменты умеют безопасно выбирать такое древо. |
| Прочитать неиндексированную метрику | Браузерный просмотр по `field-lessons.md`: приход, титул, годы, DGS/item/кадр, затем сам акт. Базовый MCP не предоставляет готового просмотрщика или пакетного скачивания метрических изображений. |

`call_operation` возвращает ограниченный JSON/текст, а не готовые файлы сканов. Не обещать OCR, полную выгрузку книги или доступ к закрытым кадрам. Не передавать неподдерживаемые фильтры как будто они сработали; расширить запрос через интерфейс либо оставить проверку в очереди. Пустой или обрезанный ответ не закрывает поиск (`familysearch-indexes.md`).

Базовый upstream не документирует Chrome-авторизацию, отдельные private-tree helpers или ежедневный импорт с журналом. У расширенного подключения использовать только фактически доступные и проверенные возможности, не выдавая локальное расширение за свойство upstream.

## 4. Из ответа API — в доказательство

Сохранить в существующем деле стабильные FamilySearch ID/ARK, запрос, фактическое покрытие и время чтения, источник с листом/кадром, исходные имена и даты. Сведения из чужого или семейного древа оценивать как утверждения его составителя; ссылки ведут к документам, которые ещё нужно прочитать. Индекс, скан, копия и повторное чтение одной записи не становятся независимыми источниками.

Оценивать отдельно содержание акта, тождество людей из разных записей и каждое родственное ребро. Один первичный акт может поддерживать `single-source`; `corroborated` требует независимых цепочек. Семейную версию владельца можно сохранять в согласованном объёме с явной пометой её происхождения, не называя её архивно доказанной.

Не объединять архивного младенца, взрослого однофамильца и человека семейного дерева по совпадению имени. До разрешения личности хранить отдельные локальные ID и явные предполагаемые соответствия. Обычная родословная линия не обозначает гипотезу: если пользователь просит показать исследовательскую ветвь, использовать реально поддерживаемые заметки/предупреждения и ясно назвать недоказанное звено. Не обещать специальный пунктир или статус, которого инструмент не поддерживает.

## 5. Разрешённая запись и проверка результата

1. Перед изменением сверить аккаунт, среду, целевое древо и ID затрагиваемых лиц. Поискать существующие карточки и проверить matches; не создавать дубль из-за другой транслитерации. Базовые write-инструменты не дают гарантии отдельного приватного tree scope.
2. Использовать подходящий guarded инструмент: `create_person`, `add_fact`, `create_couple`, `create_parent_child`, `create_source`, `attach_source`. В `create_parent_child` передавать одного или двух доказанных родителей в одном вызове, не добавляя второго по факту брака первого. Для деталей изучить фактическую схему операции.
3. Записать основание изменения (`reason`), источник, лист/номер акта и соответствующую оценку доказанности. Не заменять чужие или семейные сведения молча; противоречия сохранить. Технический успех не повышает доказательную силу.
4. Флаги `create_despite_matches`, `confirm_deceased`, `override_rights`, `allow_unverified`, `confirm_destructive` не выбирать самостоятельно ради снятия отказа: требуется явное решение пользователя по соответствующему основанию. Уже данное решение не переспрашивать. `call_operation` не выполняет production-записи; слияние людей сервером не поддерживается.
5. После записи перечитать изменённую карточку, факт, связь или источник. Сохранить удалённый ID, результат проверки и соответствие локальному ID; код HTTP 201/204 сам по себе не подтверждает нужное содержание. После тайм-аута, обрыва или неясного ответа сначала искать результат и читать его, а не повторять POST.

Upstream не обещает идемпотентность. Его общий обработчик сессии может повторить callback после 401, в том числе уже частично выполненный. Перед любой записью, даже разовой, проверить, что маршрут не переисполнит mutation callback при обновлении авторизации. Если такой повтор уже встроен и его нельзя отключить, использовать другой проверенный маршрут без replay; поручение на запись не устраняет риск дубля. Для повторяемого импорта дополнительно сохранять намерение и возвращённые ID и разрешать неизвестные исходы чтением. Не повторять неподтверждённую запись автоматически; такие операции оставить на сверку, продолжая исследование.

Изменившаяся или отозванная исследовательская версия требует пересмотра уже внесённого вывода. Не удалять людей, связи или источники автоматически из-за их исчезновения из нового экспорта. Показывать пользователю, что осталось на сайте и требует проверки.

## 6. Приватность и итог

Минимизировать сведения живых по `privacy-and-safety.md`; не выдумывать дату смерти и не выдавать оценку жизненного статуса за документально установленную смерть. Соблюдать фактические требования `confirm_deceased`. Не предполагать, что приватность отдельного дерева распространяется на загружаемые Memories: `upload_memory` создаёт публичный материал. Перед передачей частного файла учитывать согласие, права на источник и упомянутых живых людей. Цитирование источника и загрузка его изображения — разные действия.

В отчёте перечислять только проверенные изменения с FamilySearch ID и источниками; отдельно — предложения, неподтверждённые операции и блокировки. `audit_evidence.py` проверяет локальные реестры, а не удалённое древо: соответствие записей и статусов перечитать отдельно. В примеры для публикации не включать данные дела, реальные семейные ID, локальные пути или секреты.
